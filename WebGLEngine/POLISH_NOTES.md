# Polish notes — pending design conversations

Things the user has flagged as future polish work. Not yet implemented; written
down so the design intent survives when we come back to them.

## Pip character ↔ M1/M2 dialogue unification

**Goal**: unify the existing dialogue characters and 3D model rigging so the
pip character (currently SVG, says snarky things and reports KPop / PowerShell
listener events) becomes M1, the avatar character becomes M2, and both live in
the same panel.

### Current state (as of v180)

- **Pip character**: SVG-based, sits in its own panel. Speaks via the KPop
  listener path (PowerShell-driven announcements). Source: `ui/HeartbeatAvatar.js`
  and related kpop wiring in `main.js` around line 2877+.
- **M1 / M2 dialogue**: text-only. `ai/PalChat.js` parses LLM output of the form
  `M1: ... \n M2: ...` and emits per-character lines. No 3D characters wired up.
- **Avatar characters**: `face/robotFaceAvatar.js` loads `RobotExpressive.glb`
  in its own window. Standalone, not yet wired to M1/M2.
- **Asset variants**: `gpu/assetVariants.js` has comments referencing
  `palchat_dog_v1` and an M2 character avatar generated by Ollama+C3D.

### Target state

- **Pip = M1**. Replace the SVG with a skeletal `.glb` (RobotExpressive or
  similar) that can wave, dance, idle, etc. Triggered by KPop / PowerShell
  listener topics: certain canned topics map to specific animation clips
  (e.g. "build started" → wave; "tests passed" → dance).
- **Avatar = M2**. Lives in the same panel as Pip. Can also use a skeletal
  `.glb`. The M2 character is the one the PalChat dialogue parser already
  knows about.
- **Speech bubbles**: when either character "speaks" (M1 or M2 line emitted
  by PalChat, or KPop listener pushes a topic to Pip), a CSS speech bubble
  pops up next to that character with the line text. Auto-dismisses after a
  few seconds. Multiple lines queue rather than overlap.
- **Interaction**: since both M1 and M2 are in the same panel, they can
  react to each other — when M1 finishes a line, M2's next line can be
  triggered relative to that. Open question: do they look at each other?
  Eye-track via uJointMatrices on the head joint? Future polish.

### Open questions

- Which skeletal `.glb` do we use? Options:
  - Already-loaded `RobotExpressive.glb` (14 clips including Dance, Death, Idle)
  - Generate one via the AI pipeline (`palchat_dog_v1` placeholder exists)
  - Two distinct meshes so M1 and M2 visually differ
- How does the panel get positioned / sized? Currently the pip panel is one
  position; if it grows to hold two characters it needs more room.
- Does the speech bubble use the existing toast system or get its own?
  Toasts have their own animation; bubbles want to point at a character.
- What's the trigger taxonomy for KPop topics → Pip animation?
  Likely a small lookup table similar to `heightScaleFor` / `targetSizeFor`:
  `kpopAnimationFor("build_started") → "wave"`, etc.

### Files that will likely need changes when this is implemented

- `ui/HeartbeatAvatar.js` — replace SVG with skeletal model rendering
- `ai/PalChat.js` — emit events with character identity (m1/m2) so the
  panel knows which character to animate / bubble
- `ai/kpopClient.js` — map topic events to animation triggers for M1
- `main.js` — host the unified panel with both characters
- New file: `ui/speechBubble.js` for the bubble component
- Possibly a new `ui/dialogPanel.js` that owns both characters

### Why this is deferred

The current AI pipeline work (parallax → roster → mesh swap → normalize)
has built a clean foundation: material sets registry, mesh swap, animation
clips on rigged GLBs. Implementing this dialogue unification now would
fight that work; doing it after the AI pipeline is settled means we can
reuse the same swap/material-set infrastructure for M1 and M2 if desired.
