## 2. The question, and what a result would and would not mean
**THE QUESTION.** Given a numbered list of FACTS computed from the event logs of a pair of fights, and a fixed prompt, can a phone-class model write a narration of what differed in which (a) **every sentence is supported by the facts it cites** and (b) **the salient facts are covered**?
**A FAITHFUL AND COMPLETE RESULT WOULD MEAN:** this model, this prompt and this decoding produce prose the engine can check line by line, so a post-hoc note can be drafted from a result without a human re-reading the log. **IT WOULD NOT MEAN:** that the model adds value over the deterministic template narrator (which is faithful and complete by construction and is the control); that it understands why anything happened (it is forbidden to say why, and the checker rejects the words); that a bigger model or another prompt could not do better or worse; anything about the sub fights beyond twelve pairs. Whether the prose is *better* than the template's is a human judgment this round prints the means to make (word counts) and does not decide.

## 3. The material
**Pairs.** One pair = one Sea OGRE scenario flown twice by `brain/seaOgre.mjs` with three `GUNNER_THETA` defenders, once with no countermeasures and once with all three (`tools/ship/takeCountermeasures.mjs`'s own `sidesOgre`). **DEV (prompt development, may be looked at and iterated on): scenarios 1 to 4.** **REGISTERED: scenarios 101 to 112.** *Said now: those twelve were flown and read for the countermeasures hypothesis (RESULT of `brain/SUB_COUNTERMEASURES_WIP.md`). Here they are INPUTS: what is under test is the narration's faithfulness, which no earlier read touched; they are used because they are the pairs whose numbers are already committed, so every claim in a narration can be held against a record that was written before the narration.*
**Facts.** A deterministic generator turns a pair into at most 24 numbered facts `F1, F2, ...`, each one line carrying a RUN TAG (`B` base, `K` with the kit, `P` the pair), the tick AND the seconds (tick / 30, one decimal) so that no arithmetic is asked of the model, and every number it contains: the outcome and score of each run; the defenders lost in each; the OGRE's torpedoes fired in each; the first tick at which the two logs differ in an event that is not a countermeasure release (the first divergence) and the first release; every `decoyed`, `intercepted`, `hit` and `loss` event of both runs (a run's repeated releases are one fact each with their count and first tick). If a pair has more than 24 such facts the later ones of the lower-priority kinds are dropped by a fixed order the module names.
**SALIENT facts** (the coverage denominator): the two outcome-and-score facts, the two defenders-lost facts, the first-divergence fact, and every `decoyed`, `intercepted` and `loss` fact.

## 4. The prompt, the output format and the checker (all fixed here, before any model is asked)
**Prompt** (frozen text in `brain/afterAction.mjs`; DEV may change it, the registered asks use the frozen one and any change after the first registered ask is an amendment and voids that model's run): the facts, then *write 4 to 8 lines; each line begins with the ids it uses in square brackets, for example `[F3,F7]`, then one sentence; use only numbers that appear in the facts you cite, written as digits; say which run (with the kit, without) each sentence is about; do not say why anything happened; do not use the words because, so, therefore, caused, due, led, since.* Decoding: temperature 0, max 600 tokens, one ask per pair per model, no retries; **the transcript (model id as the server reports it, the parameters, a hash of the prompt, the reply) is recorded once and every later read replays it** (the convention of Round 5: a replay never asks a model and never invents an answer).
**The checker** (deterministic, `checkNarration`). A line is **PARSED** iff it begins with `[F<number>(,F<number>)*]` and has text after it. A parsed line is **SUPPORTED** iff (1) every cited id exists in the pair's facts; (2) every number written in the sentence as digits (integers and decimals, signs ignored) appears among the numbers of the cited facts, or is a small ordinal the prompt allows (the run names have none); (3) it contains none of the forbidden causal words; (4) its run is consistent: a sentence containing "without" or "no kit" cites no `K`-only fact and one containing "with the kit" cites no `B`-only fact. Anything else is UNSUPPORTED; a non-parsed line is UNPARSED (counted, never supported). Number words ("two") are not checked and polarity beyond (4) is not checked: **both are limits of the checker and are said in the report.**
**Measures per model, pooled over the twelve pairs:** FORMAT = parsed lines / all lines; SUPPORT = supported lines / all lines; COVERAGE = salient facts cited by at least one supported line / salient facts; the number of narrations whose own SUPPORT is under 0.75.

## 5. The arms and the controls
* **Model arms**: each model id a run is made with (whatever the phone has loaded; the arm is named by the id the server reports). One transcript per model.
* **TEMPLATE** (the checker's positive control): the deterministic narrator that writes one line per salient fact citing itself. It must read SUPPORT 1.000 and COVERAGE 1.000 or the checker is broken.
* **SHUFFLED** (the checker's negative control): each model's narration of pair j graded against the facts of pair i = j + 1 (the last against the first). A narration that is about the wrong fight must NOT be supported: its SUPPORT must be at most 0.50 or the checker cannot tell a narration of this fight from another's.

## 6. Checks, run first; a failure is the first line of the report and the verdicts are NOT WEIGHED
(1) The facts generator is deterministic: two generations of a pair are identical and every fact's numbers are the log's (spot-checked in the gate against the event list). (2) TEMPLATE reads SUPPORT 1.000 and COVERAGE 1.000. (3) SHUFFLED reads SUPPORT at most 0.50 for every model. (4) The transcript is whole: twelve replies, the model id and parameters of one run throughout, no duplicate pair.

## 7. The reading and the bottom line (per model, the first that applies)
1. a check failed -> `THE CHECKER IS BROKEN: THE READINGS ARE NOT WEIGHED`.
2. FORMAT under 0.50 -> `THE MODEL CANNOT FOLLOW THE FORMAT`.
3. SUPPORT under 0.90, or more than one narration under 0.75 -> `UNFAITHFUL: THE NARRATION CANNOT BE TRUSTED LINE BY LINE`.
4. COVERAGE under 0.80 -> `FAITHFUL BUT INCOMPLETE`.
5. otherwise -> `FAITHFUL AND COMPLETE`.
Printed with them, not in any reading: the mean words a narration (against the template's), the lines per narration, and which kinds of line failed (an id that does not exist, a number that is not in the facts, a causal word, a run mismatch, no ids).

## 8. Expectations, written before anything is asked
The model is a phone-sized one (about 3 to 8 billion parameters, quantized), asked for free text with citations at temperature 0. **FORMAT at least 0.90: about 55 percent. SUPPORT at least 0.90 (and no more than one narration under 0.75): about 35 percent. COVERAGE at least 0.80 given FAITHFUL: about 40 percent.** Bottom lines for a first model: CHECKER BROKEN about 8, CANNOT FOLLOW THE FORMAT about 20, UNFAITHFUL about 40, FAITHFUL BUT INCOMPLETE about 20, FAITHFUL AND COMPLETE about 12. The failures I expect, in order: a tick or a second copied wrongly; a line with no ids; a run named wrongly; a causal word in spite of the instruction. The cross-narration control should separate cleanly (SHUFFLED SUPPORT under 0.30: about 80 percent).

## 9. What will be built (new files only; nothing existing edited), and who runs what
1. `brain/afterAction.mjs` (+ gate `brain/afterAction-selfcheck.mjs` with a mutation pass in its header): `factsOf(pairRun)`, `salientOf`, `promptOf`, `parseNarration`, `checkNarration`, `templateNarration`, `coverageOf`, the transcript key. Pure.
2. `tools/ship/takeAfterAction.mjs` (+ gate): `facts --set dev|registered` (flies the pairs and prints or writes the facts), `ask --base <host:port> --key <key> --model <id> --set dev|registered --out <file>` (the transport is `ui/privateLmClient.mjs` `chatStream`; resumable; records the transcript), `report --in <file> [--in <file> ...]` (the checks, the controls, the readings, the bottom line, offline).
3. The gate exercises everything with a **scripted fake model** (a faithful one, one that miscopies a tick, one that drops ids, one that says "because", one that narrates the wrong pair), so the checker's every branch is held by a test that needs no model.
**The sandbox has no model and cannot reach the phone. So the REGISTERED READ IS OWED on the owner's side:** `ask` with the phone's (or the rig's) address and key, on `--set dev` first (to iterate the prompt, DEV only), then `--set registered` once, then `report`. The file it writes is the only thing that needs to come back. Nothing in this round is a result until that file exists.

* **A4. The checker's three small rules the registration left open.** (i) A "small ordinal the prompt allows" is a one-digit ordinal (1st .. 9th); 10th is a number. (ii) Digits glued to a LETTER before them (the 3 of the id F3) are not numbers; digits followed by letters (5s) ARE numbers. (iii) Numbers compare as numbers (2.25, 2.250 and 2.2500 are one number); signs are ignored. The causal words are matched as whole words in any case ("also", "duel", "controlled" are not causal). Fact texts contain none of the seven words and no digit that is not a measured number.
* **A5. A subtlety of the SHUFFLED control, found by a scripted model.** The control grades each narration against the facts of the NEXT pair. A model that systematically narrated the pair one ahead of each would read SUPPORT 1.000 under it and so trip the check, and every reading would be THE CHECKER IS BROKEN -- the control cannot tell that narration from the right one. The gate holds this on purpose. A model that narrates the wrong pair two ahead (or at random) is graded UNFAITHFUL as it should be.
* **A6. The ask.** The transport is `chatStream` of `ui/privateLmClient.mjs` as registered; it sends no temperature, so the fetch handed to it is wrapped to add `temperature: 0` to the request (the gate holds that the server sees 0 and 600 tokens, streamed). The model id of the transcript is the one the server reports at `GET /v1/models` (the first model's id or name), the id asked for is kept beside it as `requested`, and a server that cannot say leaves the asked id. The key goes only into the Authorization header. A reply that does not arrive whole (an HTTP error, an interrupted stream, empty text) is not recorded and stops the run; a second run of the same command goes on from the pairs without a reply ("no retries" means no re-asking of a pair that has a reply and no looping on a failure). One transcript file is one model and one set.
