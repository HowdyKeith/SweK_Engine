# gputaskman: an install page, and a one-button session that starts an Ollama model, takes GPU snapshots and saves one JSON file (UNNUMBERED; 2026-11-08)

Keith, 2026-11-08: "let's add a install link/page to swek engine that installs gputaskman. can we have swek also start the model, run gputaskman, save snapshot, and give me the json to send to you?" -- after asking whether `github.com/shanselman/gputaskman` could be used, and while trying to see a local model (Qwen3.8-27B, then a coding model) on a GTX 1080 whose 8 GB cannot hold it.

**This is a tool, not a study.** Nothing here is registered and nothing is a result: it measures a machine. What it is for is to put real numbers beside the question "does this model fit this card, and what does it cost when it does not": how much of the model sits in VRAM and how much spills into system memory, how fast it generates, and what else is using the GPU.

## 1. What exists, read from the sources and not recalled

* **gputaskman** (github.com/shanselman/gputaskman, MIT; README read 2026-11-08; the installed program's SOURCE read the same day, section 7.1): "An `htop` for what's inside your GPU, not just how full it is", "Early, experimental software". A Python terminal UI with a CLI: `--once`, `--json` (one snapshot; unavailable counters are `null`, not zero), `-i`, `--gpu N`, `--list-gpus`, `--no-host`, and a `diff` subcommand. Windows 10/11 (WDDM counters, NVML for NVIDIA, ADL for AMD), Linux and WSL (NVIDIA; AMD on native Linux), macOS Apple Silicon (from a clone). **Intel GPUs are not supported.** Installable with `uv tool install gputaskman` or `pipx install gputaskman` (Python 3.11 or newer); unsigned portable archives are on its releases page (the capture showed none). It reports per-process local GPU memory, "Spill" (GPU-accessible system RAM), an estimated non-resident commit, engine activity, detected runtimes (CUDA, HIP, Vulkan, Direct3D, ggml, ONNX Runtime) and, for language models, weights, KV-cache and compute-buffer estimates from GGUF math. **The README describes no importable library, and does not describe the shape of `--json`; its source does (section 7.1).**
* **The bridge's pattern for opt-in installs** (`ai-bridge/mlxInstallBridge.js`, read): a module required by `server.js`, one line a route, every process and network call injectable so a gate can drive every branch. `privatelm.html` (f17f8416) is the precedent for the page, the `server.html` link, the two indexes and `tools/ship/pageSections.mjs`.
* **Ollama** exposes `/api/version`, `/api/tags`, `/api/ps` (each loaded model with `size` and `size_vram`: the split between VRAM and everything else, from Ollama itself) and `/api/generate` (an EMPTY prompt loads a model; `keep_alive` 0 unloads it; the reply carries `eval_count`, `eval_duration`, `prompt_eval_*`, `load_duration`).

## 2. What was built (new files, and the lines added to three existing ones)

| file | what it is |
|---|---|
| `ai-bridge/gpuTaskManBridge.js` | the bridge side: `detect`, `install`, `snapshot`, `nvidiaSmi`, `hostInfo`, the Ollama calls, `runSession`, and the jobs wrapper `startSession` / `jobStatus` |
| `ui/gpuTaskManClient.mjs` | the page logic, pure: install choices, status lines, the session body, polling, the plain-words summary |
| `gputaskman.html` | the opt-in page: 1 what is on this machine, 2 install, 3 start a model and take the snapshots, 4 the JSON to send (copy, download) |
| `tools/ship/gpuTaskManBridge-selfcheck.mjs`, `tools/ship/gpuTaskManClient-selfcheck.mjs` | the two gates (the second also runs the page's own script against a fake DOM) |
| `ai-bridge/server.js` | one `require` and five route lines |
| `server.html`, `tools/ship/pageSections.mjs`, `page-index.json`, `launch-index.json` | the link, the drawer entry (eleven of fifteen), the two generated indexes |

**The five routes** (all JSON; only the named fields are passed on from a request body): `GET /gputaskman/status`; `POST /gputaskman/install` `{method}` where method is `uv` or `pipx` and nothing else; `POST /gputaskman/snapshot` `{gpu}`; `POST /gputaskman/session` `{model, base, numPredict, settleMs, unloadWhenDone}` (returns a job id); `GET /gputaskman/job?id=`.

**The session, in order:** detect (what is installed, whether Ollama answers and has the model) -> baseline snapshot (gputaskman `--once --json` and an `nvidia-smi` query, if each exists) -> load the model through Ollama's HTTP API -> `/api/ps` and a snapshot with the model resident -> a short generation (the fixed prompt, 200 tokens unless changed) with `/api/ps` and a snapshot taken WHILE it runs (after a 2.5 s settle) -> `/api/ps` after -> optional unload. One file: `brain/rig-results/gpu-snapshots/gpusnap-<time>-<model>.json`. A session that fails part-way still saves what it has (a baseline with Ollama down is still worth sending).

**What the JSON holds:** `schema`, `kind: "gputaskman-session"`, the start and finish times, `ok` and `error`, the request (model, the Ollama address, tokens, the fixed prompt), `host` (OS, release, architecture, CPU model and count, total and free memory in GB, the Node version), `ollama` (version, whether the model was already pulled, load time in ms, `/api/ps` after the load, during the generation and after it, the generation's own timings and rates), `gputaskman` (found, working, its GPU list), `snapshots.baseline|loaded|busy` (gputaskman's JSON, stored as it comes), `nvidiaSmi.baseline|loaded|busy`, `steps` (a log with times), `summary` (model size, GB in VRAM, percent on the GPU, tokens per second, load seconds).

## 3. Using it (cmd, on the rig). THESE STEPS ARE ALSO ON THE PAGE ITSELF (the "How to use this, step by step" card), AND THE PAGE'S NOTES ROW (the shared one every page with notes carries: `brain/PAGE_NOTES_WIP.md`) LINKS THIS NOTE AND `RIG_COMMANDS_2026-11-07.md` AND CAN SHOW EITHER IN PLACE (the engine serves a `.md` file as a download, so the page reads the text itself). Added 2026-11-08 after Keith asked whether the instructions were on the page or linked from it: they were neither.

1. Start the engine's bridge as usual (default port 8787), open `http://localhost:8787/gputaskman.html` (or the **gputaskman** link in `server.html`).
2. **Check this machine.** It reads uv, pipx, Python, gputaskman and Ollama.
3. **Install with uv** (or pipx). If gputaskman installs but the page still says it cannot find it, restart the bridge from a NEW terminal: uv and pipx add `~/.local/bin` to the PATH for new shells only (the bridge also looks in `~/.local/bin` itself).
4. Type the model exactly as `ollama list` shows it (pull it first with `ollama pull <name>` if needed; Ollama must be running: the Windows app starts it). Press **Start the model, run gputaskman, save a snapshot**. A large model can take minutes to load; the progress box shows each step.
5. When it finishes the JSON is in the box, saved in `brain/rig-results/gpu-snapshots/`, and can be copied or downloaded. **Look at it, then send it: gputaskman lists the programs using the GPU.** The file holds no host name, user name or path of its own.

## 4. Safety properties (each held by a gate row)

* `install` runs one of two fixed argument vectors chosen by name from a frozen table; any other string (`__proto__` and `constructor` included) is refused with no command run. No command goes through a shell (`execFile`, `shell: false`).
* The only Ollama this module will talk to is a loopback one (`127.0.0.1`, `localhost`, `[::1]`; no credentials, no path); a LAN address is refused before a request is made.
* The saved file's name is built from a timestamp and the model name with everything outside `[A-Za-z0-9._-]` replaced; it cannot leave its folder.
* `--gpu` takes a whole number 0 to 63 and nothing else.
* **Said plainly:** the bridge has no origin check (it never had one: `Access-Control-Allow-Origin: *`), so any web page open in the same browser can ask it to run these routes. What they can do is fixed and small (install one named package with a named tool, load a model into a local Ollama, run gputaskman, write one JSON file into one folder), and it is the same exposure as `/mlx/install` and `/mlx/pull`. The package comes from PyPI through uv or pipx, unpinned and unscanned.

## 5. NOT DONE, NOT CHECKED, said plainly

* **It has not run against a real Ollama or a real GPU. It HAS run against the real gputaskman 0.3.3, found installed in the sandbox on 2026-11-08, which has no GPU and so prints empty snapshots (section 7.4).** What was run: the gates (every command, request, clock, timer, file system and OS faked), and one end-to-end smoke with the REAL module, the REAL route lines pulled out of `server.js`, REAL child processes (shell scripts standing in for `gputaskman`, `nvidia-smi` and `uv`) and a REAL HTTP server on loopback standing in for Ollama. That smoke passed; it proves the plumbing, not the programs.
* **The shape of `gputaskman --json` is not described in its README**, so the snapshots are stored exactly as printed (a banner before the JSON is skipped); since 2026-11-08 the watch also READS a few fields of version 0.3.3 from them (section 7), taken defensively. If the first real snapshot is not what is expected, that is the first thing to look at.
* **Windows is untested.** The code looks for `gputaskman` on the PATH and then in `~/.local/bin` (with `.exe`), tries `python`, `python3` and `py` for the version (the Microsoft Store stub for `python` exits non-zero and is skipped), and runs `nvidia-smi` by name. None of that has seen a Windows machine.
* **A model with thinking on by default** will spend part of the generation's tokens thinking; the speed figure counts tokens either way, and the saved reply head shows what came back. The fixed prompt and 200 tokens are a probe of speed, not of quality.
* **The session does not start Ollama and does not pull weights;** it says so and says how.
* The generation request, if the session is interrupted part-way, keeps running inside Ollama until it ends; the bridge does not cancel it.

## 7. THE WATCH: sample for N seconds, and the GPU brain run under the samples (added 2026-11-08)

Keith, 2026-11-08: "build 'sample for N seconds' option. also, gputaskman may show it as Direct3D under the browser's GPU process. lets do that too." (the answer to "would gputaskman give us any insight to how our swek 'gpu brain' is running?", which said it could show which process uses the card and under which runtime, but that one snapshot cannot catch a 3 to 10 ms decision call, so a series is what it needs).

**This is still a tool, not a study.** Nothing here is registered; the swarm's own timings in a watch file are NOT a result and are never written to `brain/rig-results/gpuSwarm.jsonl`.

### 7.1 What I found by reading the real thing, said first
**gputaskman 0.3.3 is installed in this sandbox** (`uv tool`, `/root/.local/bin/gputaskman`, found during this round) and runs; with no GPU its `--once --json` prints an empty snapshot (`vram_total` 0, `processes` an empty list, `device` null). Its source (`gputaskman/report.py`, `telemetry.py`, `cli.py`) answers what the README does not:
* **The JSON.** Top level: `taken`, `gpu`, `driver`, `cuda` (a KEY, not a runtime: a word search of the text finds "cuda" in every snapshot, which is why the module reads fields and does not search words), `adapter`, `vram_total`, `vram_used`, `shared_used`, `backend`, `device` (the NVML or driver telemetry: `util_gpu`, `util_mem`, `mem_used`, `temp`, `power_w`, `sm_clock`, `mem_clock`, `pstate`...), `processes`. Per process: `pid`, `name`, `kind`, **`runtimes`** (a list such as Direct3D, Vulkan, CUDA, ggml), `vram_bytes`, `shared_bytes`, `committed_bytes`, **`gpu_pct`** and **`engines`** (a share per engine type, WDDM counters), `ports`, `model_files`, and for language-model servers an `llm` block.
* **A one-shot snapshot takes at least a second**: `--once` samples twice, a second apart, because engine utilization is a rate (and on WSL waits up to 15 s for the Windows counters). Add the Python start. So "every 500 ms" is a floor: the real gap between snapshots is the snapshot's own time, and `tookMs` in the file says it.
* **A one-shot looks at GPU 0 unless `--gpu N` is given.** On a machine with more than one adapter, section 1's list (`--list-gpus`) shows which is 0; the watch routes take a `gpu` field but the page has no box for it yet.

### 7.2 What was built
| file | what changed |
|---|---|
| `ai-bridge/gpuTaskManBridge.js` | `runWatch` / `startWatch` / `watchParams` / `watchSummary` / `readSnapshot`, the sampler (`sampleLoop`, `takeSample`, `fit`), the limits `WATCH` and `BRAIN`; `runSession` takes `sampleSeconds` and `sampleIntervalMs`; the jobs wrapper is shared (one job at a time, `kind` session or watch); `gpuArg` factored out of `snapshot`; `runCmd` takes a working directory |
| `ai-bridge/server.js` | `POST /gputaskman/watch` (six routes now) and two more named fields on the session route |
| `ui/gpuTaskManClient.mjs` | `watchBody`, `watchLines`, the limits `SAMPLE` and `BRAIN`, the sampling field of `sessionBody`, `ROUTES.watch`, a watch file's download name |
| `gputaskman.html` | section 4 (watch: A sample for N seconds, B run the GPU brain and watch it), section 5 the JSON, a sampling box in section 3, the caution and steps text, the buttons lock together |

**The two modes.** `sample`: N seconds (3 to 300, default 20), a snapshot every interval (500 to 10000 ms, default 1000), nothing started: the owner runs the thing. `brain`: two snapshots, then **`node tools/ship/gpuSwarm.mjs --hardware --sizes <list> --rounds <1..5> --seconds <1..20>`** (the engine's own swarm: the CPU twin, then one GPU dispatch a tick; `--seconds` is SIMULATED flight, 30 ticks a second; sizes only from 64, 256, 1024, 2048, 4096, 8192; defaults 4096 and 8192, 2 rounds, 10 s), a snapshot every interval while it runs, two after. At most 120 snapshots; **never `--write`**. If the browser fell back to a software adapter (the swarm's first line says `*** SOFTWARE ADAPTER ***`) the watch is NOT ok and says the card was not used. The file is `brain/rig-results/gpu-snapshots/gpuwatch-<time>-<mode>.json`.

**What the file holds**: every sample (`tMs` since the start, `tookMs`, `phase`, the gputaskman snapshot whole, the nvidia-smi answer, and a small digest `read` of the snapshot that survives the size budget), `brain` (the swarm's command, exit code, duration, the adapter line, `software`, its output), and `summary`: nvidia-smi utilization and memory before / during / after with the rise; gputaskman's own utilization, SM clock and power; **`programs`** (by name: runtimes, GPU share peak and median during, memory peak, engines, and `onlyDuring`, true for a program first seen while the swarm ran) and **`runtimes`** (which programs ran under Direct3D, Vulkan, CUDA while it ran). The size budget is 3 MiB of full snapshots; later ones are kept as their verdict, time and size, and `summary.omittedSnapshots` counts them.

The session takes the same series: `sampleSeconds` (0 = off, the default) samples while the test answer is generated (`phase` "generate"; `summary.sampled`).

### 7.3 Using it (on the rig, after the model session)
In section 4 of the page: **A** press Sample now, then start the thing you want watched; or **B** press Run the GPU brain and watch it (about two minutes at the defaults, a browser opens). Look at the summary: the question is whether the browser's GPU process appears (`chrome.exe` or `msedge.exe`, whichever the harness's Chromium is), under which runtime, with what share, and whether `onlyDuring` is true. Send the file. If `runtimes` for the browser reads "no runtime named", that is an answer too: gputaskman did not tell Direct3D from nothing for that process.

* **Said plainly, the exposure:** the bridge still has no origin check, so any web page open in the same browser can ask it to start a watch, which runs the swarm tool (a browser and a busy card for up to 30 minutes, the limit) with only the allow-listed numbers above. Same class as `/mlx/install`; one job runs at a time.
