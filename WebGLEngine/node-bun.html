This writes (or removes) ~/.voxelbridge/use_bun.flag, which the launcher reads on the NEXT boot — it does not restart anything now. The full runtime picker with the rest of the fleet is on runtimes.html.

The one dependency Bun lets you skip

Measured on this tree: of the eleven optional packages /runtime probes, exactly one resolves under Bun and not under Node — ws, and Bun ships it built in (Bun.resolveSync("ws") returns a bare name, not a file path, and a real WebSocketServer listens).

That is not cosmetic. ai-bridge/server.js line 116 does try { require("ws") } catch and falls back to a null-object WebSocket server — the bridge boots, and live push is silently off. So on a box with no ws installed, running under Bun turns live updates ON. Every other one of the eleven is missing under both.

What was measured, and what was not

On Linux with Bun 1.3.11: all 134 ai-bridge bridge modules load, ai-bridge/server.js boots and serves /health, tools/ship/verify.mjs runs ALL GREEN, and every capability probe matches Node — child_process, dgram, worker_threads, cluster included.

That was Linux. The rig is Windows, where Bun's process, socket and native-module surfaces are its weakest, and a green run in a Linux sandbox is evidence about that sandbox. The buttons above exist so the question can be answered here instead of inherited from somewhere else.

One bug the survey did find and fix: /health reported process.version, which Bun emulates — under Bun it answered v24.3.0 on a box whose real Node was v22.22.2, naming a Node newer than any installed. There is a runtime field now.
